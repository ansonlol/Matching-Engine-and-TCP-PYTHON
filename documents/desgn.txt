## 1. Responsibilities (tighten)

**Order Entry (Gateway)**  
- Accept client connections  
- Decode framed Protobuf  
- Validate basic fields  
- Forward to matcher (or risk first)  
- Return **ack / reject / own fills** to **that** client  

Not its job: full matching logic, fan-out to all traders.

**Matching Engine**  
- Own the book  
- Match on cross; else rest  
- Emit **trades** and optionally **book updates**  

Not its job: TCP to every market-data user, long-term history.

**Market Data**  
- Subscribe clients  
- Broadcast trades / top-of-book / snapshots  
- Handle slow consumers  

Not its job: accept orders.

## 3. Trade-offs — how to talk about them

Use a simple pattern every time:

> Option A vs Option B → I choose X because Y for this system.

### Order Entry

| Topic | Options | Typical choice |
|--------|---------|----------------|
| TCP vs UDP | Reliable vs lossy | **TCP** for orders (must not lose cancels/acks) |
| Threading | Thread per client vs async | Either; don’t block matcher on slow clients → **queue** |
| Parse where | Gateway vs engine | Parse in gateway for early reject |

### Matching Engine

| Topic | Options | Typical choice |
|--------|---------|----------------|
| Writers | Many threads + locks vs **one thread** | **One writer** (your design) — simpler correctness |
| Memory | In-memory vs DB each order | **In-memory** for speed; journal if you need restart |
| Latency vs throughput | Ultra-low latency vs batching | Trading: low latency; still batch MD if needed |

**Your single-thread point is correct.**  
Add: “Slow MD clients must not block matching → matcher only publishes to a queue, MD service fans out.”

### Market Data

| Topic | Options | Typical choice |
|--------|---------|----------------|
| TCP vs UDP | Reliable vs fast multi-receiver | **UDP multicast** common for public MD; **TCP** for simplicity/recovery |
| Snapshot vs only deltas | Bandwidth vs easy join | Snapshot on subscribe + deltas after |
| Slow consumer | Buffer / drop / disconnect | Cap buffer; disconnect or drop with sequence gap |

**Your TCP-for-orders / UDP-for-MD split is a classic good answer.**

## 5. Failures / restarts (what you said you don’t know)

Learn **these** patterns — enough for Tuesday:

### Client disconnect (Order Entry)
- Connection drops mid-order  
- Gateway closes socket; optionally cancel “session orders” or leave GTC until client reconnects  
- **Trade-off:** cancel-on-disconnect vs leave resting (depends on product)

### Matcher crash
- In-memory book **lost**  
- **Mitigations:** write-ahead log (journal), snapshot + replay, or accept “restart empty” for a toy  
- Gateways get errors / reconnect  

### MD packet loss (UDP)
- Client sees **sequence gap** → request **snapshot** over TCP  
- Or use TCP MD only (simpler, slower scale)

### Slow MD client
- Don’t block matcher  
- Drop or disconnect that client  

### Duplicate orders
- Client retries after timeout  
- Need **idempotency** (client order id) so add isn’t applied twice  

**One sentence you can reuse:**  
> “Matcher stays in-memory for speed; on crash we lose state unless we add journaling. Orders use TCP so we don’t lose acks; MD can use UDP plus snapshots to recover from loss.”

## 6. Scale later

| Component | How to scale |
|-----------|----------------|
| Order Entry | Run **many gateway** processes; load balance clients |
| Matcher | **Shard by symbol** (AAPL book on core 1, TSLA on core 2) — one writer **per book** |
| MD | Multicast; or dedicated MD cluster; separate network |
| Risk | Scale reads; still careful on position updates |

**Not:** “add risk service” as the main scale story for the matcher — risk is a **feature/path**, scaling matcher is **sharding / partitioning**.

History/previous day → **storage service** or DB, not the live matcher hot path.

## 7. A strong 2-minute spoken answer (template)

> Order entry terminates client TCP sessions and speaks Protobuf with framing. It forwards to a single-threaded matching engine so the book has one writer and stays consistent. Trades go back to the originating client and also to a market-data component that fans out to subscribers—often UDP for speed, with snapshots for recovery. We test the book with unit tests and the path with multi-client integration tests. On failure, we assume in-memory state is lost without a journal; clients reconnect and may resync. To scale, we add gateways and shard matchers by symbol.

Memorize the **structure**, not every word.
